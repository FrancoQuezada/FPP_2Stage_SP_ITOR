\section{Computational methodology and evidence protocol}
\label{sec:computational}

The computational design has two separate purposes. First, it compares
exact methods for the tree-based stochastic optimization problem. Second,
it assesses a tree-optimized placement on the paired original propagation
graphs. This section documents the inputs and settings specified by the
current implementation. Because the available repository snapshot does not
contain nonempty final run files, those settings describe a reproducible
\emph{configured protocol}, not a verified completed experiment.

\subsection{Instances, samples and settings}

The current instance configuration names a reduced 20-by-20 landscape
and its Reburn pair (\texttt{new20x20}), and a reduced 40-by-40
landscape and its Reburn pair (\texttt{new40x40}). Their declared sizes
are 400 and 1,600 cells. It also names a 10,000-cell pair, but the repository's
preflight documentation flags that pair's metadata as inconsistent; it
must not enter the reported comparison without correction. Source Cell2Fire
message files and per-scenario arc lists are absent from the repository
snapshot. In particular, the realized rooted-tree property and exact
paired arc inclusion still require an instance-level validation on the
input files used for a final experiment.

The full experiment launcher defaults to 100 and 200 training scenarios,
five samples for \texttt{new40x40}, and the focused launcher to 100 training
scenarios and ten samples for \texttt{new20x20}. Training IDs are drawn without
replacement from 1--9000; the prescribed independent test set is the
fixed set of IDs 9001--10000. Within a sample, all compared methods must
receive identical training and test ID files. The launcher budgets use
$\alpha\in\{0.01,0.02,0.03\}$, a 1,800-second time limit, a requested
relative gap of $10^{-3}$, and one solver thread. For CVaR, the
configuration specifies $\beta=0.9$; the mixed objective additionally
sets $\lambda=0.5$. By default the weight map is homogeneous, so a unit
loss counts burned cells. The solver build configuration points to IBM
ILOG CPLEX Studio 22.1.1, but the version actually used by a run, its
hardware and operating system must be read from the final run provenance.

The focused 20x20 launcher uses a smoke-method subset by default, whereas
the full method file enumerates the complete comparison. Thus, combining
outputs of the two launchers without checking method coverage would
produce unmatched panels. Likewise, script defaults alone do not certify
which samples, weights or options were executed. Every comparison in
Section~\ref{sec:results} must be keyed by landscape, scenario IDs,
replication, $\alpha$, risk settings, weight map, time limit and requested
gap, with missing or duplicate runs reported rather than silently pooled.

\subsection{Compared exact methods}\label{sec:compared}

The full method file gives seven configurations per risk objective, for
21 labels in total. Table~\ref{tab:methods} identifies the differences
that matter scientifically. The LP-dual baseline with \texttt{RootCuts} uses
one root user-cut round; projected families additionally use a configured
maximum of 100 root separation rounds and 100 projected cuts per round,
with violation tolerance $10^{-3}$. These are limits, not guaranteed
counts of rounds or cuts. Standard LLBI is an initial scenario inequality;
the projected exponential variants generate their structural cuts at the
root. Every LP-dual configuration retains integer-candidate optimality
separation. Neither projected polynomial method is present in this full
campaign method file, although both help explain the bound relationships
in Section~\ref{sec:methods}.

The combinatorial variants use the distinct cut construction implemented
for graph propagation and motivated by the network-spread Benders work of
\citet{taninmics2024benders}. Their initial scenario inspection fraction
is 0.10; uninspected scenarios are checked before accepting an integer
candidate, preserving the exact acceptance rule. Their ascending or
descending order affects computational work, not the finite-scenario
objective. These variants do not inherit the LP-dual baseline's root-cut
setting. No method's superiority is implied by the presence of a
strengthening feature; its effect must be measured in matched runs.

\subsection{Evaluation and reporting}\label{sec:evaluation}

For each solved or time-limited tree model, let $y^T$ be its best
available \emph{feasible} placement. Its in-sample tree loss is computed
on the training IDs under $G_s^T$. In a second, paired calculation, the
selected cells are transferred by original Cell2Fire cell identifier
and $Q_s^R(y^T)$ is evaluated for those \emph{same} training IDs.
For example, the empirical expected discrepancy is
\begin{equation}\label{eq:paired-delta}
 \widehat\Delta_{\rm pair}(y^T)
   =\frac{1}{|\mathcal S_{\rm train}|}
     \sum_{s\in\mathcal S_{\rm train}}
         \bigl(Q_s^R(y^T)-Q_s^T(y^T)\bigr).
\end{equation}
When the paired-graph assumptions hold, every summand is nonnegative.
We retain the absolute discrepancy as the primary quantity, since a
relative discrepancy would be undefined if Reburn loss were zero. The
worker writes a separate paired-evaluation status; this status and the
mapping completeness must be checked before using its numbers.

Finally, the tree placement is evaluated on previously unused IDs
9001--10000 under the \emph{tree} representation. This is the ordinary
out-of-sample assessment; the paired training-ID evaluation is not an
independent test. For a matched set of losses, expected loss, empirical
VaR at $\beta=0.9$ and empirical CVaR defined by \eqref{eq:cvar}
summarize average and upper-tail performance. With positive weights that
are not all one, these are weighted-loss metrics; burned-cell counts
must be reported separately.

Optimization performance is reported through status, feasible objective,
best lower bound, certified relative gap and elapsed wall time. A run at
the requested gap is distinguished from a proven optimum, and a
time-limited incumbent is never labeled optimal. The principal paired
method comparisons use solved count, final gap, root bound, B\&B nodes,
cut counts and time where present; a mean runtime over all runs must
account explicitly for censored runs. Numerical tables also require
the executed solver version, hardware, actual weight map, complete
manifest and final nonempty run files.
